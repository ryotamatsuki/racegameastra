# ミニ四駆ブラウザレーシングゲーム仕様書

版：1.0  
作成日：2026-09-08  
対象：https://github.com/ryotamatsuki/racegame  
公開先予定：https://ryotamatsuki.github.io/racegame/  
状態：実装前の仕様。公開先の稼働を示すものではない。

## 1. 目的と完成形

プレイヤーが立体的なミニ四駆の機種を選び、各種パーツを組み替え、その結果をレースで確かめられるブラウザゲームを作る。
ガレージで模型を触る楽しさ、セッティングの試行錯誤、滑らかなレース観戦を一つの体験にする。
日本語を既定とし、インストールやログインなしでPCとスマートフォンから遊べるようにする。

参考は https://storm-race.vercel.app/ とユーザー提示画像である。
画像から確認した要素は、作業机上のマシン展示、機種選択、部品カテゴリ、分解展示、部品拡大、立体コース、複数台レース、順位と周回表示、複数視点である。
参考サイトは確認環境でWebGL 2要件による起動エラーが出たため、走行物理、実測FPS、各パーツの効果は未確認である。
以下は本プロジェクトの独自設計であり、参考サイトの内部実装を推定した仕様ではない。

## 3. 画面と操作の流れ

起動 → ガレージ → コース選択 → レース前確認 → カウントダウン → レース → 結果 → 改造または再挑戦。

### 3.1 起動

タイトル、初回案内、読込進捗、音の有効化、画質設定を用意する。
起動時にWebGL 2の利用可否を判定する。
非対応時は日本語で理由と再試行ボタンを表示し、黒画面や無限ローディングにしない。
音声はユーザー操作後に開始する。
素材取得失敗には対象と再試行手段を表示する。

### 3.2 ガレージ

木製の机、緑系のカッティングマット、工具、部品トレー、照明を背景にする。
中央のマシンを主役とし、UIで覆わない。
PCは中央に車体、右に性能、下に部品カテゴリと候補を配置する。
スマホは折り畳める性能パネルと横スクロールの部品候補を用意する。

ドラッグで回転、ホイールとピンチでズームする。
「分解表示」ではボディー、シャーシ、駆動系、タイヤ、ローラー、電池等を対応する方向に離す。
「組み立て」で正しい位置に戻る。
部品選択時は対象を強調し、名称と説明を表示する。
交換や分解中に連続操作しても重複生成や位置ずれが起きないようにする。
「視点を戻す」「標準構成に戻す」「保存」「レースへ」を用意する。

### 3.3 レース画面

順位、周回、経過時間、速度、区間名、簡易コース図、マシン識別色を表示する。
速度は模型のシミュレーション上の速度としてkm/h表示する。
演出用のスケール速度を追加する場合は、その旨を明示して実速度と混ぜない。

PCは1〜5でカメラ切替、Spaceで一時停止と再開、Rで確認後に再挑戦する。
Spaceでページがスクロールしないよう、ゲームにフォーカスがある場合だけ既定操作を抑止する。
スマホには同じ機能のタッチボタンを用意し、ホバーに依存しない。
アプリが非表示になったら停止し、復帰時に再開操作を求める。

### 3.4 結果

4台の順位、総時間、各周タイム、完走状態、自車の構成を表示する。
ベスト更新と前回との差を表示する。
「コーナー減速が大きい」「着地で失速」等の助言は記録した走行イベントに基づく。
根拠のないランダムな助言は出さない。
同じ構成とseedで再挑戦するボタン、ガレージへ戻るボタンを設ける。

## 4. マシンとパーツ

実在製品やアニメの名称、ロゴ、固有形状をそのまま転用せず、オリジナル名称と造形で制作する。
参考サイトの素材やソースの取得を実装前提にしない。

| 仮の機種名 | 外形の特徴 | 標準構成の傾向 |
| --- | --- | --- |
| AERO FALCON | 低いノーズと幅広い翼 | 直線速度重視 |
| TORQUE BISON | 厚い中央部と短い車体 | 加速と登坂重視 |
| CORNER LYNX | 細いボディーと広いローラー配置 | コーナー重視 |
| BALANCE ORCA | 滑らかな一体形状 | 安定性重視 |

色替えだけで4機種と数えない。
車体はボディー、キャノピー、左右タイヤ、ホイール、前後ローラー、バンパー、シャーシ、電池、モーター、ギヤ、翼を識別できる立体形状にする。
最初の標準構成はすべて入門コースを完走可能にする。

| カテゴリ | 選択例 | 走行モデルへの入力 |
| --- | --- | --- |
| ボディー | 軽量、標準、安定 | 質量、重心、空気抵抗 |
| シャーシ | 軽量、剛性、低重心 | 質量、重心高、駆動効率 |
| モーター | 高回転、高トルク、バランス | 回転数、トルク、消費 |
| ギヤ | 速度型、中間、加速型 | 減速比、伝達効率 |
| タイヤ | 小径、大径、高グリップ | 半径、摩擦、転がり抵抗 |
| ローラー | 低摩擦、標準、安定 | 横方向支持、接触抵抗 |
| 電池 | 軽量、容量型、出力型 | 質量、電圧特性、容量 |
| ウイング | 小型、標準、安定型 | 質量、空気抵抗、ゲーム上の安定補正 |
| ブレーキ | 弱、中、強 | 特定区間の減速、着地前の速度 |

空力や安定補正はゲーム用近似として扱い、実車の実測値や忠実な再現と称しない。
データにはID、名称、説明、互換タグ、質量、対応する物理値、表示モデルIDを持たせる。
数値は単位を明記し、一元管理する。
見た目の変更と物理パラメータの変更を同じ装着データから導く。

全機種共通の装着規格を基本にし、互換性がないものは選択不可と理由を表示する。
交換前に速度、加速、コーナー、安定性、持久力、総重量の差を確認できるようにする。
性能バーは共通の基準で物理値または標準ベンチ走行から算出し、機種名に固定した架空の値にしない。
装着部品と異なるモデル、無効な保存データ、存在しないIDを安全に検出する。

## 5. レースとコースの定義

### 5.1 コース構成

| コース | 内容 | 検証したい選択 |
| --- | --- | --- |
| WORKSHOP OVAL | 直線、緩いカーブ、小さな坂 | 最高速度と加速 |
| TECHNICAL RIDGE | 連続カーブ、バンク、登坂、下り、ジャンプ | トルク、グリップ、ブレーキ |
| SKY LOOP | 垂直ループ、立体交差、高架、ジャンプ | 進入速度と安定性 |

4本の固定レーンを使い、初回はレーンチェンジと車体同士の衝突を省略する。
各レーンの長さと曲率を個別に計算する。
CPUも自車と同じ走行モデルを使い、隠れた速度補正や結果の事前決定を入れない。
難易度はCPUの公開された装着構成で調整する。

内外レーンの長さによる有利不利をゼロと称しない。
初回の通常レースはレーンを表示し、固定seedから割当を決定する。
比較用タイムアタックは全構成を同じ基準レーンで測る。
順位は共通チェックポイントに基づく周回と区間進捗で計算し、各レーンの走行距離だけを比較しない。

### 5.2 状態と終了条件

レース状態は loading、ready、countdown、running、paused、finished とする。
マシン状態は onTrack、airborne、recovering、finished、dnf とする。
3周完了時はゴール通過時刻を補間して記録する。
同タイムは同順位で表示し、一覧順だけIDで安定化する。
停止や逆走でゴール判定を繰り返さない。

標準モードはコースアウト後に最後の通過済み安全地点へ復帰する。
復帰中もレース時計を進め、2秒の停止時間を設ける。
同一車両が3回コースアウトしたらDNFとする。
レース上限は180秒とし、未完走車をDNFにして結果へ進む。
ゴール済み車は記録を固定する。
リトライでは時計、周回、入力、物理状態、音声、カメラを初期化する。

## 6. 走行モデル

### 6.1 設計方針

描画と走行計算を分離する。
通常走行は走路上の移動を制約したモデル、ジャンプと逸脱は空中運動を使う。
すべての部品を剛体として逐次衝突計算することは初回に求めない。
専用の物理エンジンを採用する場合も、この仕様との対応と追加依存の理由を記録する。

固定時間刻みは1/120秒を初期値とし、描画間を補間する。
処理遅延時はサブステップ数を制限し、無制限の追いつき計算をしない。
大幅な遅延は停止扱いとし、知らない間に周回を進めない。
seed、構成、コース、入力イベントから同一エンジン環境で再現できるようにする。
ブラウザ間の浮動小数点の完全一致までは保証しない。

### 6.2 座標と駆動

世界座標はY-up、単位はm、kg、s、N、radとする。
各レーンを弧長sでサンプリングし、位置、接線、走路面法線、横方向、曲率、バンクを取得する。
ループ頂点や接続点で姿勢が反転しない連続フレームを使い、閉路の継ぎ目も検証する。
車輪の回転は移動距離と半径から求め、車体姿勢は走路フレームに沿わせる。

駆動力はモータートルク曲線、減速比、タイヤ半径、効率から導く。
近似例は F_drive = torque(omega) * gearRatio * efficiency / tireRadius とする。
omegaは車速とタイヤ半径と減速比から求める。
加速度は駆動、転がり抵抗、空気抵抗、重力の接線成分、ブレーキを合算して質量で割る。
発進時、速度ゼロ、高回転域、電池低下で数値が破綻しないようにする。
高グリップにしただけで最高速度が直接加算されるような無関係な補正を避ける。

### 6.3 カーブとループ

曲率に応じた必要加速度と、路面接触およびローラー支持で許される範囲を比較する。
超過時は減速、横方向の揺れ、一定時間を超えた場合の逸脱へ段階的につなぐ。
乱数だけでコースアウトを決めない。
各定数と閾値は調整可能なデータにし、単位と意味を説明する。

垂直ループは重力と曲率による法線方向の力を扱い、接触維持に必要な支持力の符号を確認する。
速度不足で路面に吸着したまま一周させない。
コースの法線方向と符号規約をテストし、頂点での接触喪失を再現できるようにする。
ループ途中での復帰地点は入口側の安全地点とする。

### 6.4 ジャンプと電池

ジャンプでは離陸位置と接線速度を初期値にして、重力下で運動させる。
着地は同じレーンに属する着地面との交差を検出する。
高架と下の走路を取り違えないよう、単純な世界Y座標判定にしない。
高速時に面を通り抜けないよう、移動区間の交差を調べる。
着地位置、姿勢、速度から失速または逸脱を決める。

電池はレース開始時に満充電にし、負荷に応じて容量を消費する。
初回の短いレースでも出力型と軽量型の差が確認できる設定にする。
消費式と質量差を説明し、実製品の電池寿命予測とは区別する。

## 7. 描画と素材の品質

Three.js、TypeScript、Viteを基本とし、UIはReactを採用する。
Reactの状態更新で毎フレーム全画面を再描画せず、走行と描画のループを独立させる。
物理、データ、UI、音、カメラを分離し、一つの巨大なコンポーネントに集約しない。

マシンはGLB/glTFまたは保守可能な手続き的メッシュで作る。
箱と円柱だけの仮置きを完成品としない。
専用モデルが作れない場合も、押し出し形状、面取り、キャノピー、翼、ホイール、塗装模様で機種差を作り込む。
素材生成サービスや有料APIがなくても必須機能を完成できる経路を持つ。

PBR材質で樹脂、金属、ゴムの違いを出し、適度な反射と接地影を加える。
静的な背景は影の焼込み等で軽量化できる。
ガレージでは精細なモデル、レースでは軽いモデルを切り替えてよい。
照明、露出、色管理をそろえ、過剰な光や被写界深度でマシンを隠さない。
カメラは壁や机へのめり込みを避け、切替時の急な回転や上下反転を抑える。

素材はリポジトリ内に保存し、実行時の外部CDNや無断ホットリンクを必須にしない。
assetsの出典、作者、ライセンス、加工、生成手順をASSET_SOURCES.mdに記録する。
生成した独自素材も出自を記録する。
ユーザーのSNSスクリーンショットそのものの公開アップロードは前提にしない。

## 8. 音とアクセシビリティ

モーター音の高さを回転数に連動させる。
スタート、ゴール、着地、部品交換の効果音を用意し、音量調整とミュートを保存する。
一時停止と画面切替で音が重複しないようにする。

UIはHTMLの実ボタンを使い、フォーカス表示とキーボード操作を用意する。
状態は色だけで区別せず、名称やアイコンも表示する。
タッチ領域は44 CSS px以上を目安にする。
動きを減らす設定では自動演出カメラと大きなUIアニメーションを抑える。
縦画面では横向きを案内するが、操作不能の全面ブロックにはしない。

## 9. 性能と互換性

次は保証済み実績ではなく、実装時の測定目標である。

| 対象 | 目標 |
| --- | --- |
| PC、中画質、1920×1080 | レース中60fpsを目標 |
| 実スマホ、中または低画質 | 30fps以上を最低目標、60fpsを推奨目標 |
| 初回必須転送量 | 圧縮後15MB以内を目標 |
| 4台レースの描画 | ドローコール200以下を初期予算 |
| 繰り返し操作 | 10回の再レースでメモリが単調増加しない |

60秒の計測区間を設け、端末、OS、ブラウザ、解像度、画質、中央値とp95フレーム時間を記録する。
平均FPSだけで滑らかと判定しない。
暖機や素材読込中は区別する。
未測定端末を対応確認済みと書かない。

DPR上限、影解像度、背景詳細、ポストエフェクトを画質設定で調整する。
まず描画解像度と影を調整し、UIの文字は読みやすく維持する。
GPU資源、イベント購読、音源は画面終了時に適切に解放する。
WebGLコンテキスト喪失時には停止と復帰案内を用意する。
対象は実装時点のChrome、Edge、Firefox、SafariおよびiOS Safari、Android Chromeとし、確認済み範囲を明記する。

## 10. 保存と構成

localStorageはスキーマ版を持ち、破損、不明ID、容量超過、アクセス拒否でもゲームを続けられるようにする。
保存できなければ端末保存不可と表示し、メモリ内で続行する。
初回のオンライン通信は静的素材の取得に限定する。
バックエンド、秘密鍵、外部AI APIは不要とする。

推奨構成：

- src/game/simulation/：DOMに依存しない走行とレース進行
- src/game/rendering/：シーン、モデル、材質
- src/game/cameras/：各カメラと補間
- src/game/audio/：音源管理
- src/data/：機種、パーツ、コース、調整定数
- src/ui/：画面と操作
- src/storage/：保存スキーマと復元
- public/assets/：配信用素材
- tests/：モデル検証とブラウザE2E
- docs/：仕様、実装判断、検証記録
- .github/workflows/：CIと公開

部品構成から導出する車両性能、レース状態、描画オブジェクトを別の型で扱う。
コースデータと表示用メッシュの参照元を共通にし、見える路面と走る経路を一致させる。

## 11. GitHub Pagesの公開

公開予定URLは https://ryotamatsuki.github.io/racegame/ とする。
Viteのbaseは /racegame/ とし、画像、音、モデル、ワーカー等のURLもbaseを尊重する。
SSRや実行時Nodeサーバーに依存しない。
画面遷移はアプリ内状態またはhashを使い、Pagesでの再読込404を避ける。

GitHub Actionsはmainへのpushとworkflow_dispatchで公開する。
PRでは型検査、モデルテスト、ビルドを実行し、公開ジョブを動かさない。
Nodeと依存パッケージの版を互換性確認後に固定し、lockfileを保存してnpm ciを使う。
Actionsの版も実装時に公式資料で確認する。

公開手順は、検証、dist生成、Pages設定、artifactアップロード、deploy-pagesの順とする。
必要な権限はcontents: read、pages: write、id-token: writeを基本にする。
github-pages環境と公開の同時実行制御を設定する。
Settings > PagesのSourceをGitHub Actionsにする。
設定権限が不足した場合は、失敗理由とユーザーが行う設定だけを具体的に残す。
別ホスティングへの置換はしない。

公開後はトップページだけでなく、/racegame/配下の素材読込、直接再読込、ガレージ操作、レース開始と完走を確認する。
Actions成功とゲーム動作成功を別々に報告する。

A06では、同じseedだけでなく、同じレーンで比較する。
A05とA08は検証用の単純な直線、カーブ、ループも使用し、複合コースだけで原因を推測しない。

WebGLが使えないCIやクラウドブラウザでは描画試験をBLOCKEDとし、PASSに置き換えない。
ヘッドレス試験と実GPUでの目視確認を区別する。

## 13. 実装順序と引継ぎ

1. 環境、型、データ、最小ガレージと1台の走行を接続する。
2. 4機種、部品交換、分解表示、保存を完成する。
3. 4台の競走、3コース、固定時間刻み、ジャンプとループを完成する。
4. カメラ、音、結果助言、スマホ、画質設定を仕上げる。
5. 受入試験、実測、修正、GitHub Pages公開を行う。

各段階で動く状態をコミットし、docs/IMPLEMENTATION_STATUS.mdに完了、未完了、次の作業を残す。
最終的にdocs/QA_REPORT.mdへA01〜A16のPASS、FAIL、BLOCKED、証拠、環境を記録する。
docs/ARCHITECTURE.mdにモジュール関係、数式、単位、調整定数、保存スキーマを説明する。
仕様変更が必要な場合は理由と影響を記録し、必須機能を無断で削って完成扱いにしない。
